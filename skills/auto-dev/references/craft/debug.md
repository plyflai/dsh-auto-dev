# 排障

在真实执行失败、行为异常或结果不稳定时使用。普通 partial 不是技术失败。

## 先看最近改了什么

用户说「之前好好的，现在不行了」，先查近因：`git log --oneline -10`、`git diff` 看最近的提交与未提交改动，问一句上一次正常是什么时候、中间有没有改过代码、配置或依赖。新对话不知道最近刚上线了什么，这一步最便宜，也最常直接命中。

## 先搭能变红的循环

动手猜原因之前，先有一个能反复跑的复现。按代价从低到高选：失败的测试 → 命令行或 `curl` → 最小脚本 → 浏览器自动化 → 回放日志或 trace → 新旧版本对比 / `git bisect` → 让用户按固定步骤操作。

这个循环要满足四条，缺一条就还不算复现：

- 能针对用户说的那个症状变红，不是只证明「程序没崩」；
- 结果稳定；时好时坏的问题，固定跑 N 次，记下复现率；
- 快到能支撑多轮试验；
- 不靠人手就能跑；非要人操作时，把步骤写死、写短。

修好后用同一个循环看它转绿；时好时坏的问题，用同样的 N 次看复现率归零。

## 缩小问题

先保存实际症状、错误和触发条件。能复现时建立最小复现；不能稳定复现时明确标记观察，不把猜测写成根因。

从最有区分度的一个假设开始，用日志、调用链、数据或最小实验验证。优先检查实际输入、状态和边界。连续同一失败时改变定位方法，而不是只换措辞重跑。

修复后验证原触发条件与受影响路径。相关新成功证据能更新判断；无关成功命令不能证明缺陷已修复。

## 修完之后

- 扫同型：根因确定后，搜索同一写法、同一调用方式或对称路径上的其他位置。确实是同一缺陷的一起修；不确定的列出来，不顺手改。
- 选修复层：判断该修在症状所在处，还是修在产生错误值的源头。修在源头能覆盖更多调用方，但影响面更大；选哪一层，按[影响分析](impact.md)核对。
- 防复发：补一条在修复前会失败、修复后会通过的检查，并真的看它在修复前失败过一次。做不到时，说明原因。

## 紧急止血之后

用户要先止血时，只做最小改动让症状消失。止住之后补三件事：在复盘里写一条，标明是临时止血、根因还没查透；把为排查临时加的日志、开关删掉；交付时建议用户再开一次彻底排查。

## 产出

说明症状、证据支持的原因、修复和验证。未知机制保留为 observation，可附假设与下一次辨别办法；有复用价值再记录 learning，不要求固定五段。

调查可继续时继续。`blocked` 用于真实阻塞，写清缺少的前提；不得因技术失败次数把排障伪装成等待用户。
